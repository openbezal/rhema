# Transactional local operator profile

This #140 foundation builds on our session archive draft #202. Settings, Bible selection, broadcast themes/output configuration and onboarding now share a native app-data `operator-profile.sqlite3`. It prepares a single persistence boundary for later preference application; archive viewing is still read-only and this branch does not implement restore, machine mapping or new-session reset.

On first use, all three legacy JSON files are read and checked before migration commits. Missing files mean empty objects. Existing invalid UTF-8, malformed/non-object JSON, nonregular files and files over 64 MiB reject migration. Original files remain byte-for-byte unchanged. A schema version, three object sections and revision are installed together in an explicit SQLite transaction. Subsequent reads use the canonical database, and do not silently fall back to older legacy files after corruption or an unsupported version.

Writes validate every supplied section, acquire an immediate transaction, compare the expected revision, update the sections and revision together, and acknowledge only after commit. A real SQLite trigger failure after the first section update verifies rollback after reopening. Reads take a consistent transaction snapshot. New Unix database files use mode 0600; existing permissions are preserved. The connection requires a durable journal mode and uses FULL synchronous policy. Future schema rejection precedes journal configuration. The app owns a serialized, lazily opened connection; native commands use a fixed app-data path, blocking-worker execution and the main window identity guard. There is no caller-supplied path.

The shared frontend section adapter keeps existing hydration, debounce and get/set/delete/save APIs. It shares one checked hydration, detaches returned objects, orders native writes and advances cache revision only after a valid acknowledgement. Failed staged edits remain retryable; newer staged edits survive completion of an older save. Receipts contain only changed sections so gain edits do not return unrelated theme images. Actual store integration tests forbid the old plugin-store route and cover all four consumers, neighboring sections, stable translation codes, local credentials and unknown keys. A queued Bible choice rechecks its current selection before writing; this is not a complete import/reset maintenance barrier.

Unreadable startup preferences do not attach persistence subscriptions that replace data with defaults. A warning stays visible until restart, since a later successful read cannot retroactively hydrate every consumer that already fell back. The tutorial does not start in this state, and the blocking Bible selection dialog explains that a choice is for the current session. Ordinary save failures retain the existing store console warnings and do not introduce a general recovery UI; the adapter supports a subsequent retry, and actual settings changes exercise that path.

## Evidence and limits

Native tests cover complete migration with Unicode/local synthetic credentials/unknown keys, preserved original bytes, canonical precedence, failed migration followed by repair/retry, invalid and oversized sources, corrupt/future canonical data, private new Unix files, stale/empty/oversized writes, coherent snapshots, partial receipts and an actual mid-transaction failure. Metadata/version and wrong-root JSON errors do not include saved credential values. The checked Bible preference command reads the same canonical section and retains its previous response shape.

The browser fixture uses the actual production app and `main.tsx` startup at 1024×600. Native storage, database content, audio and outputs are mocked; synthetic storage persists through sessionStorage solely for reload testing. Initial BIUO, gain, Unicode custom theme and monitor mapping load through the real stores. Gain and KJV edits survive reload while the fake local key and unknown setting remain intact. An injected disk-full failure preserves the saved revision and gain; the next edit saves successfully. Unreadable startup shows guidance, suppresses onboarding, and a temporary language choice leaves the saved revision unchanged with zero writes. Deliberate failure modes produce expected console warnings; no unexpected browser error was observed.

Before release, test actual installed packages on macOS, Windows and Linux with representative existing profiles, filesystem permission failures, interrupted migration/write, and process restart. Verify native dialogs and portable preferences separately. Local credentials remain local plaintext storage, as before; portable exports still exclude them. Preserved legacy files are a migration fallback artifact, not an automatically maintained downgrade copy: returning to an older release would otherwise read the original pre-migration settings. Preserve the canonical database when planning rollback. This branch does not claim packaged migration/restart acceptance or completion of #140.
