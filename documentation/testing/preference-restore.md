# Staged portable preference restore

This #140 slice builds on our transactional operator profile draft #203. Opening session or preferences JSON remains read-only. The saved reference has a separate **Review preferences** action. Review shows portable settings and theme names, maps stable Bible codes to installed translations, and requires an explicit choice for an unavailable primary or secondary edition. None is an explicit secondary choice. Canceling review changes no imported preference. A successful restore preserves the current transcript, Queue, detections, committed Live content, local credentials, microphone, output assignments, active theme and onboarding. Imported custom themes receive fresh IDs and are appended as copies.

Restore requires stopped transcription, Live off, a readable profile, closed Theme Designer and no pending output or language change. A synchronous maintenance lease pauses app-owned detection, navigation, preview, presentation, keyboard and remote consumers before asynchronous work. Existing callbacks and pending start/on-air/presentation work check epochs or operation revisions. Native transcription start also uses a generation handshake, and the stopped-session lock serializes the actual commit against a concurrent start. These guards protect this restore boundary; they do not implement the separate new-session reset or a complete durable session journal.

Before importing, settings, Bible and broadcast persistence drain their timers and the shared profile queue. The controller waits for every flush, including after a failure, and rechecks eligibility. The exclusive adapter freezes writes and validates the complete native acknowledgement before publishing the corresponding stores synchronously. Publication does not schedule redundant persistence writes. Normal rejected commits release maintenance without publishing imported values. Local edits flushed before the import remain saved; a rejection does not rewind those legitimate earlier saves.

The main-window native command runs on a blocking worker and uses the fixed app-data profile. It validates the real Bible database, unique installed codes, bounded scalar settings and theme IDs/counts. It builds all three updated sections from the canonical profile to preserve local and unknown fields, commits them in one SQLite transaction with the expected revision, then assigns the native active Bible ID without a remaining fallible step. The frontend validates the complete theme schema; Rust validates restore scalars and theme metadata/identity rather than duplicating the entire theme schema. Archives with the previous 0–10 gain range remain readable; applying preferences accepts the current 0–2 audio range.

A missing or invalid acknowledgement cannot prove whether a commit happened. That path holds maintenance and profile writes in recovery, keeps the current in-memory frame and session available, and offers JSON/TXT export before an explicit reload. The old webview broadcast snapshot is removed **before** native commit, so an interrupted reload cannot override canonical imported preferences. A confirmed rejection restores a valid old snapshot; successful publication writes a new one. Late output status callbacks cannot recreate the old snapshot during recovery. Reload loses volatile transcript and Queue state, so export first and verify surviving native outputs afterwards.
